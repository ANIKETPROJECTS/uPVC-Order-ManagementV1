========================================
E. EVERYTHING DYNAMIC (very important)
========================================
No hardcoded stages, statuses, colours-by-name, locations, clients, installers or counts anywhere in the dashboard.
1. Stages, statuses, payment states, glass states: read from the same enums/config tables the rest of the app uses. If a new stage or status is added in the software later, it must automatically appear in the pipeline, donut, filters, chips and legend (assign colours from a palette by index if no colour is configured).
2. Filter options (clients, locations, installers, assignments, glass vendors) come from the database, only values that exist.
3. Widget registry: build the dashboard from a registry of widgets { id, title, permission, endpoint, defaultVisible, defaultOrder, size }. New modules can register a widget without editing the page layout.
4. Master Admin can customise: show/hide widgets and reorder them (simple "Customize" drawer), saved per user (and optionally as a company default). Provide "Reset to default".
5. Role-based: widgets and money values hidden for roles without access; Master/Super Admin see all.
6. Every widget refetches on: filter change, date change, manual refresh, auto-refresh tick, and window focus. Use one shared query key set so they update together. Show "Updated hh:mm:ss".
7. "Priority & reports" view: every KPI, chart, pipeline stage, attention row and table row must deep-link to the relevant module page with the same filters pre-applied. Add an "Export" menu in the hero (Dashboard summary as PDF/print and CSV of current Recent Orders + Attention list) so the Master Admin can take reports directly from the dashboard (the standalone Reports section has been removed).
8. Add widgets automatically when data exists in modules not yet shown (Quotation approvals, Measurement sheets, Glass tracking, Payments collected vs pending, Dispatch, QR production progress, Overdue items) — as per the widget registry, hidden when empty.
