PART 1 OF 2: BACKEND for Dispatch Numbering. Do NOT build UI in this part.

Implement Dispatch Numbering in my existing order-management app. Read the current Orders, Lot register, Windows, Dispatch desk, QR status update, Documents, Permissions and Activity/User log code first, then reuse existing patterns, services and permission system.

CLIENT REQUIREMENT (confirmed)
Append a dispatch number (D1, D2, ...) to the Order ID and Lot to track how many times a lot has been dispatched. Example: R2637-L1-D2 = second dispatch of Lot 1 under order R2637.
Confirmed rules:
- The D counter is PER LOT. One order can have multiple lots; each lot has its own D1, D2... independent of other lots.
- Lot format is L1, L2 (no zero padding). Existing "L01" style codes must become "L1" everywhere.
- A whole lot is dispatched together. NO partial dispatch and no window-level selection.
- A lot can have MULTIPLE active dispatches at the same time. D2, D3... can be created at any time, even while D1 is still planned, dispatched or in transit. Do NOT block creation based on the status of earlier dispatches. Each dispatch is independent and numbered sequentially per lot.
- Each lot dispatch has its own QR code and delivery challan.

1. DATA MODEL
- New table `dispatches`: id, order_id, lot_id, dispatch_no (int), dispatch_code (e.g. P1431-L1-D2), dispatch_note (optional free text, e.g. "2nd truck", "replacement"), status (planned | dispatched | delivered | returned | cancelled), dispatched_at, delivered_at, delivery_location, vehicle_no, driver_name, driver_phone, challan_no, windows_snapshot (JSON), qr_token (unique, non-guessable), qr_revoked_at, created_by, created_at, updated_at.
- There is NO dispatch type (first / re-dispatch) and NO mandatory reason. The D number is simply the sequential count of dispatches of that lot.
- NO dispatch_items table. The windows of a dispatch are the lot's windows. Snapshot their list, dimensions and area into `windows_snapshot` at creation so later edits never change old challans.
- Unique constraint (lot_id, dispatch_no). Generate dispatch_no inside a DB transaction with a row lock on the lot so concurrent requests never create duplicates. Numbers are never reused; cancelled dispatches keep their number.
- Code format lives in ONE helper: <order_code>-L<lot_no>-D<n>. Keep it configurable in one place.
- Lot code migration: change lot display/code from L01 to L1 everywhere (lot register, windows, documents, QR, search, activity log, communication templates). Keep old "L01" strings searchable as an alias so old references still resolve.
- Block deletion of lots/orders that have non-cancelled dispatches.
- Backfill: for every lot of orders currently Dispatched or Installed, create D1 (status delivered for Installed, dispatched for Dispatched) with windows_snapshot. Fix existing mismatches between order lifecycle and dispatch status (for example lifecycle "Dispatched" but dispatch status "Installed"). Make the migration idempotent and reversible, and tell me to take a backup first.

2. API
- POST /dispatches (order_id, lot_id, dispatch_note, delivery_location, vehicle_no, driver_name, driver_phone, challan_no, remarks)
- GET /dispatches with filters: full-code search (also old L01 style), order, lot, status, client, date range, sort, pagination
- GET /dispatches/:id
- PATCH /dispatches/:id (details and status; moving to dispatched/delivered records timestamp + user)
- POST /dispatches/:id/cancel (reason required, revokes QR token)
- GET /dispatches/:id/challan.pdf
- GET /dispatches/:id/qr.png
- GET /dispatches/by-token/:qr_token (sign-in protected, used by the QR page)
- Creation is allowed whenever the lot is ready (all windows have frame, shutter, glass = Ready). There is NO restriction based on existing dispatches of the same lot. Admin override with mandatory reason (logged) for lots that are not ready.
- Order and lot summaries must expose: dispatches_count, latest_dispatch_code, latest_dispatch_status, per-lot state (not dispatched | dispatched | delivered), and order-level counts (lots_dispatched / lots_total).
- Permissions: dispatch.view / create / edit / cancel / override. QR token endpoint requires sign-in plus dispatch.view; status change requires dispatch.edit.
- Log every create / edit / status change / cancel in the User log and in `activity_events` (create the table if it does not exist: id, type, order_id, actor_id, message, meta JSON, created_at).
- Challan: generate the PDF server-side with company header, dispatch code (large) + QR, order and client details, delivery location, lot number, windows table from windows_snapshot (window id, type, dimensions, area) with totals, vehicle, driver, challan no., date, note/remarks, and signature boxes (dispatched by / received by). Store each generated PDF in Order Documents under that dispatch; regenerating keeps version history.

3. LIFECYCLE DERIVATION
- The order's Dispatched stage is reached as soon as ANY lot gets its first dispatch (status dispatched or delivered). Orders where only some lots are dispatched show a derived "partially dispatched" flag.
- The order is "fully delivered" only when every lot has at least one Delivered dispatch and no dispatch of that order is still planned or in transit.
- Stop writing "Dispatched" and "Installed" manually from the order QR "Update order status" endpoint. Reject those values there (or redirect to the dispatch flow) so lifecycle and dispatch records can never disagree. Installation stays in the Installations module.
- Remove "Installed" from dispatch statuses.

4. EDGE CASES
Editing windows after a dispatch (warn the user, do not change old challan snapshot), orders with only the default required lot, two users creating dispatches for the same lot at the same time, two active dispatches of one lot at once (D1 in transit + D2 planned), cancelled dispatch keeps its number and its QR stops working, Asia/Kolkata timezone for all dates, permission checks on QR endpoints.
